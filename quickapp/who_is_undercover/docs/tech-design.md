# 《谁是卧底》腕上多人派对游戏 —— 技术方案(定稿)

> 本文为技术定稿。手表端传输层采用 `@system.fetch` 短轮询(快应用 API 白名单不含 WebSocket/Socket),
> server-authoritative 架构不变。方案内不再依赖任何平台不支持的能力。

## 一、作品概述

- **作品名称**:《谁是卧底》腕上多人派对游戏
- **所属赛道**:快应用(手表应用创新)
- **目标平台**:openvela 快应用框架,运行于智能手表(manifest `deviceTypeList: ["watch"]`)

**作品简介**:把经典桌游《谁是卧底》搬到腕上设备,做成一款抬手即玩的多人派对游戏。一名玩家担任主持人控场,4–8 名朋友无需任何额外道具,用各自的手表完成「创建/加入房间 → 私密查看身份 → 轮流口头描述 → 投票 → 公布出局与胜负」的完整对局。主打「随时随地、轻量社交」的腕上娱乐场景。

游戏中玩家**面对面口头描述**词语进行博弈,手表担任**控场端与发牌端**——负责房间管理、身份/词语的私密下发、回合推进、计时提醒与票数判定;手表之间**不传输音频**,同步的是对局状态。

## 二、核心功能

1. **房间与组队**:一人创建房间生成房号 / 二维码,其他人加入,支持 4–8 人同局。
2. **真人主持模式**:房主 / 指定玩家担任主持人,手表即主持端——一键开局发词、按序点人描述、发起投票、宣布出局与胜负;普通玩家端只看到自己的身份与词语。
3. **发牌与身份**:系统自动分配「平民 / 卧底」身份与词语对,本机私密查看,杜绝剧透,减轻主持人负担。
4. **回合制流程**:描述 → 投票 → 公布的回合循环,腕上计时与震动提醒,主持端汇总票数、判定胜负。
5. **词库管理**:内置多主题词库,支持随机出题与难度选择;可选叠加 AI 出题。
6. **多设备协作**:各手表通过服务端中转同步房间与对局状态,保证主持端与玩家端一致。

## 三、创新亮点

1. **腕上轻交互**:针对小屏与抬腕场景重新设计交互(大按钮、震动反馈、私密查看身份),把复杂桌游压缩到几步可玩;主持端与玩家端差异化 UI。
2. **AI 智能出题**:接入 ai_agent + MiMo LLM,自动生成高质量、难度可调的近义词对,避免词库重复、提升可玩性。
3. **秒级状态同步**:基于服务端权威状态 + 客户端轮询的多端同步。回合制玩法对延迟不敏感,秒级同步在体验上与长连接无可感差异,却完全落在快应用 `fetch` 的能力边界内,可真机稳定跑通——**技术选型服从平台约束,是本方案的务实取舍**。
4. **系统级能力展示**:服务端裁剪响应实现「私密下发防剧透 + 权威判定防作弊」、震动/计时/二维码等腕上原生能力的组合运用。

## 四、设计原则(技术取舍)

- **命名明确**:手表担任控场 / 发牌端,玩家面对面口头描述,**手表之间不传输音频**,不使用「语音」作为卖点,避免歧义。
- **传输走 HTTPS 轮询,不用长连接**:快应用 API 白名单**不含 WebSocket/Socket**,手表端无法持有服务端长连接。因此采用「客户端动作用 `fetch` POST 提交、客户端每 1–1.5s `fetch` GET 拉取本视角状态快照」的**短轮询**方案。跨网段可用、无需 P2P,且在能力边界内。
- **服务端权威(server-authoritative)**:房间、身份、词语、票数、胜负判定全部在服务端计算,手表端只做展示与输入——既保证多端一致,又天然防作弊防剧透。
- **响应按视角裁剪**:服务端对每次轮询响应**按 playerId 裁剪**,只返回该玩家有权看到的信息(自己的词、当前阶段允许公开的票数),从传输层根治剧透。
- **交付节奏**:单机可玩版本作为最小可交付(P0),多端同步与 AI 能力作为增量叠加。
- **AI 能力分级**:AI 出题(近义词对生成)为核心亮点;AI 卧底为远期探索项,不列入初赛与决赛的演示计划。

## 五、总体架构

```text
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  主持端(表)  │     │  玩家端(表)  │ ... │  玩家端(表)  │
│ host client │     │ player      │     │ player      │
└──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       │  HTTPS             │                   │
       │  ├─ POST 动作      │  轮询 GET 状态     │
       │  └─ GET  轮询状态  │  (每 1~1.5s)       │
       └─────────────┬──────┴───────────────────┘
                     ▼
             ┌───────────────┐
             │  游戏服务端    │  房间管理 / 权威状态机 /
             │  Game Server  │  按 playerId 裁剪响应
             │ (Node.js/Go)  │  （HTTPS，带证书）
             └───────┬───────┘
                     │  出题请求（可选，开局时一次）
                     ▼
             ┌───────────────┐
             │  AI 出题服务   │  ai_agent + MiMo LLM
             │  (velaclaw)   │  近义词对生成
             └───────────────┘
```

**分层职责:**

- **手表端(快应用)**:UI 渲染、用户输入、私密查看身份、震动/计时;`fetch` 提交动作 + 定时拉取本视角状态;**不持有权威状态,不做长连接**。
- **游戏服务端**:唯一权威状态源(房间、身份分配、回合、票数、胜负判定);对每个轮询请求按请求者身份裁剪响应。
- **AI 出题服务**:服务端在开局时请求一次,生成「平民词 / 卧底词」近义词对。

## 六、核心数据模型

服务端完整状态(**绝不整体下发**):

```json
{
  "roomId": "8421",
  "status": "waiting | playing | voting | revealed | finished",
  "hostId": "player_1",
  "round": 2,
  "version": 17,
  "players": [
    { "id": "player_1", "name": "小明", "role": "host", "alive": true },
    { "id": "player_2", "name": "小红", "alive": true }
  ],
  "wordPair": { "civilian": "咖啡", "undercover": "奶茶" },
  "assignments": { "player_1": "civilian", "player_2": "undercover" },
  "votes": { "player_2": "player_3" },
  "speakingOrder": ["player_1", "player_2", "player_3"]
}
```

> - `wordPair` / `assignments` 仅存在服务端,**永不下发**;每个玩家端只在自己的视角快照里收到「你自己的词」。
> - `votes` **按阶段裁剪**:`voting` 进行中,响应中不返回他人投票(防从众/被带节奏);仅在 `revealed` 阶段返回完整 `votes`。
> - `version` 单调递增:客户端携带上次的 `version` 轮询,服务端可据此判断是否有变更,减少无效渲染与传输。

## 七、通信协议(HTTPS 轮询)

采用 HTTPS 请求-响应。客户端「动作」用 POST 提交,客户端「拉取状态」用 GET 轮询;服务端不主动推送。

**客户端动作(Client → Server,POST):**

| 动作 | 端点 / 载荷 | 说明 |
| :--- | :--- | :--- |
| `create_room` | `POST /room` `{ name }` | 创建房间,返回 `{ roomId, playerId }` |
| `join_room` | `POST /room/{roomId}/join` `{ name }` | 加入房间,返回 `{ playerId }` |
| `start_game` | `POST /room/{roomId}/start` `{ playerId }` | 房主开局(触发 AI/词库出题 + 分配身份) |
| `submit_vote` | `POST /room/{roomId}/vote` `{ playerId, targetId }` | 玩家投票 |
| `next_phase` | `POST /room/{roomId}/next` `{ playerId }` | 房主推进阶段(描述 → 投票 → 公布) |

**客户端拉取(Client → Server,GET):**

| 请求 | 端点 | 说明 |
| :--- | :--- | :--- |
| `poll_state` | `GET /room/{roomId}/state?playerId=X&since=version` | **轮询本视角快照**,每 1–1.5s 一次 |

**服务端本视角快照响应(裁剪后):**

```json
{
  "version": 17,
  "status": "playing",
  "round": 2,
  "phase": "describe",
  "players": [ { "id": "player_1", "name": "小明", "alive": true } ],
  "speakingOrder": ["player_1", "player_2", "player_3"],
  "timer": { "endsAt": 1719800000000, "seconds": 30 },
  "yourWord": "咖啡",
  "yourRoleVisible": false,
  "voteResult": null
}
```

> - `yourWord` 只在响应里给**请求者自己**——这是防剧透的关键,由服务端按 `playerId` 裁剪实现,等价于「定向单发」,且实现更简单。
> - `timer.endsAt` 用**服务端绝对时间戳**下发,端上只按本地时钟做倒计时展示,规避各端时钟漂移(见第九节)。
> - `voteResult` 仅在 `revealed` 阶段非空,含 `{ votes, out, winner? }`。

## 八、游戏状态机(服务端权威)

```text
waiting ──start_game──▶ playing(describe)
                            │ next_phase
                            ▼
                        voting
                            │ 全员投票 / 房主 next_phase
                            ▼
                        revealed（公布出局者）
                            │ 判定
                     ┌──────┴──────┐
                （未分胜负）      （分出胜负）
                     │                │
                     ▼                ▼
              playing(describe)   finished
```

- 每次状态迁移由服务端计算,`version` 自增;手表端在下一次轮询拿到新快照后按 `phase` / `voteResult` 渲染。
- 胜负判定:卧底全部出局 → 平民胜;卧底存活且人数 ≥ 平民 → 卧底胜(规则可配置)。

## 九、手表端(快应用)实现要点

- **网络**:仅用 `@system.fetch`(白名单内,manifest 声明 `{ "name": "system.fetch" }`)。服务端**必须 HTTPS 带有效证书**——快应用明文 HTTP 请求通常被拦截。
- **轮询启停(功耗关键)**:在 `onShow` 用 `setInterval` 启动状态轮询,在 `onHide` / `onDestroy` **立即 `clearInterval` 停止**;避免息屏/切后台仍在拉取耗电。轮询间隔 1–1.5s,`voting`/`revealed` 等关键阶段可临时提高到 1s。
- **请求防抖与容错**:动作按钮点击后置 loading 防重复提交;单次轮询失败不弹错,连续失败 N 次再提示「网络不稳定」并保留上一帧状态。
- **差异化 UI**:同一 rpk 内按 `role` 渲染——主持端有「开局 / 点人 / 发起投票 / 下一阶段」控制条,玩家端只有「我的身份词 + 投票」。
- **私密查看身份**:传表发牌时仅展示当前玩家的 `yourWord`,确认后切换下一位,避免旁人瞥见。
- **腕上交互**:大按钮、单屏单任务、关键节点震动(`@system.vibrator`:轮到你描述、进入投票、出局公布)。
- **计时**:以服务端 `timer.endsAt` 为准,端上仅按本地时钟做倒计时展示,不各自计时,规避漂移。

## 十、AI 能力落地

**AI 出题(核心亮点):**

- 服务端在 `start_game` 时请求 AI 出题服务,生成「平民词 / 卧底词」近义词对(如 咖啡/奶茶、老虎/狮子)。
- 落地:服务端调用 ai_agent(或直接调 MiMo LLM API),prompt 约束「输出一对易混淆但有区分度的近义词、附难度分级」。
- 好处:避免内置词库重复、支持难度调节、可按主题生成。
- **兜底**:AI 请求失败或超时,服务端回退到内置词库,开局不受影响。

**AI 卧底(远期探索项,不列入演示计划):**

- 设想:人数不足时由 AI 顶替一名玩家,看到自己的词后生成一句不暴露身份的描述并参与被投票。
- 该能力涉及博弈式生成,工程复杂度高、稳定性难保证,**仅作远期探索方向**,初赛与决赛均以真人局为准。

## 十一、分阶段落地计划(MVP 优先级)

| 优先级 | 内容 | 验证方式 |
| :--- | :--- | :--- |
| **P0(初赛保底)** | 单机版:发牌 / 身份 / 回合 / 投票 / 词库 + 腕上交互,「一块表轮流看」 | 单模拟器即可演示(已验证,见 [test-report.md](test-report.md)) |
| **P1(初赛主体)** | 服务端中转的多端轮询同步(先 2~3 端)+ AI 出题 | 多模拟器实例 + HTTPS 服务端;或手机网页模拟玩家端,录 demo 视频 |
| **P2(决赛/加分)** | 真机多表联机、打样外壳样机 | 决赛真机调试 |

> **第 0 周先做连通性验证(前置于所有游戏逻辑)**:先跑通「手表模拟器 `fetch` 一个 HTTPS 服务端、POST 一条动作 + GET 轮询回一条状态」的最小闭环,确认①模拟器能出网访问云服务端、②HTTPS 证书被接受、③多个模拟器实例能各自持有独立 `playerId`。这条链路不通,后续全部无从谈起,故排在最前。
>
> **初赛演示策略**:手表应用创新赛道初赛用模拟器验证。多端同步用「多个模拟器实例 + 服务端」跑通并录制可回放 demo;真机多表联机放到决赛(可申请真机样机)。

## 十二、风险与规避

| 风险 | 规避 |
| :--- | :--- |
| **快应用无 WebSocket** | 已改为 `fetch` HTTPS 短轮询;回合制对延迟不敏感,秒级同步体验等价 |
| **服务端须 HTTPS** | demo 服务端配有效证书(如 Caddy 自动证书 / 云厂商证书);第 0 周先验证模拟器可访问 |
| 多端同步在初赛难演示 | 服务端中转 + 多模拟器实例 + demo 视频;真机联机留决赛 |
| 轮询耗电 | `onShow` 启、`onHide`/`onDestroy` 停;间隔 1–1.5s;非活跃阶段可降频 |
| 单次轮询失败 | 保留上一帧状态,连续失败 N 次才提示;不因偶发抖动打断对局 |
| 时钟漂移导致计时不一致 | 计时以服务端 `timer.endsAt` 为准,端上只做展示 |
| AI 出题质量/延迟不稳定 | prompt 约束 + 内置词库兜底,失败即回退本地词库 |
| AI 卧底复杂度高 | 作为远期探索项,不列入演示计划,先保真人局跑通 |
